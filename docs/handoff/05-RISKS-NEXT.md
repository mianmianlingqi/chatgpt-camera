# 已知限制、待排查风险与下一步

这里区分“已确认实现限制”和“源码提示的待复现风险”，不把静态阅读推断写成已发生故障。

## P0：验证核心交付

实际 Codex 附件链路未验证。DesktopTarget.cs 要求选中 UIA 项 AutomationId 含 GUID，当前 Codex 是否暴露此结构未知。先读取真实 UIA 树并记录脱敏结构、会话切换前后标识，再决定适配修改。完成标准：多个不同会话均能正确识别；正常拍照实际看到对应附件；切换会话时不误贴。

## P0：投递安全的现有限制

最终 Observe 与 SendInput 不是原子操作，用户在两者间切换仍存在竞争风险。附加成功判据是删除附件按钮数量增加，可能误把同时发生的其他附件变化当成本次成功。需用受控切换/同时添加照片试验复现，评估更可靠的附件身份及结果确认机制；结果不确定保留 unconfirmed。不能仅放宽检查。

## P1：Android 异步与生命周期（待复现）

MainActivity 的 activeId、activePairing、reserveSucceeded 由多个异步回调共享；快速后台/前台、网络延迟、重拍可能让晚回调影响新的拍摄。Activity 销毁后回调及 executor 关闭也需检查。用延迟网络、相机重开和连续拍摄复现，必要时改为每次拍摄不可变上下文及可取消生命周期任务。完成标准是每张 JPEG、ID、配对和预留目标始终对应。

## P1：补传旧地址（源码行为已确认，故障待网络复现）

重试比较保存配对的 pin 与当前所选 pin，但传输仍使用照片 JSON 中原始 host/token。DHCP 改变电脑 IP 后，重新扫码可能仍向旧 host 补传。测试同证书换 IP；若修复，保持身份验证与原始目标失效规则，仅在验证为同一接收端后更新连接地址。

## P1：队列、保留与崩溃一致性

1000 条容量包含无 JPEG 的预留，取消/失败可消耗名额；无清理界面。手机已传输照片也保留，pending() 在主线程扫描 JSON，积累后可能卡顿。JPEG 和 JSON 分别落盘，崩溃可能留下孤立文件；没有自动对账。先设计明确清理/保留行为，再测试满队列、磁盘满和落盘中断，不直接删除用户照片。

## P1：桌面调用与平台差异

WaitAsync(3s) 是等待超时，不保证底层 UIA 调用被取消。需检查慢/挂起 UIA 对后续请求影响。
进程路径白名单和编辑框命名规则可能不覆盖未来/不同安装的 Codex。正常服务监听全部 IPv4，实际防火墙和多网卡路由尚未验收。

## P2：发行与体验

APK 仅 debug 签名；尚无正式签名管理、CI、Android instrumentation 测试或设备矩阵。
相机旋转、前摄回退、扫码弱光、EXIF 与预览差异没有实测。
缺少照片保留期、批量管理和更细的传输/附件状态可见性；有些网络等待可能超过用户对“立即”的预期。

## 推荐接手顺序

先做 P0 实机与 UIA 诊断 → 针对实际失败修改适配器 → 复测会话切换/重复/重启 → 复现 Android 生命周期和 IP 补传 → 补齐队列与正式发行。
每个任务独立提交，变更触及协议或状态机时跑现有断言并新增覆盖真实失败的测试。纯文档修改只检查内容/链接/版本，不需要假装重跑程序测试。
